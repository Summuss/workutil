# 04: 把截图粘贴进 Memo

**What to build:** 让截图可以直接粘进正文,和它要说明的那段文字挨在一起 —— 这是记事本做不到、也是本功能存在的主要理由之一。

**保存是原子的**:编辑期间图片只以 Blob 形式存在于浏览器内存,正文里使用临时引用;保存时正文与所有新图片在**同一个请求**内提交,后端在该请求中落盘并把临时引用改写为最终引用。这样就不存在「图片已上传但 Memo 尚未创建」的中间态,因而不需要暂存区、不需要草稿记录、也不需要孤儿清理任务。代价是编辑途中浏览器崩溃会丢失尚未保存的内容,对「随手记」这个场景可以接受。

图片以**原图**存储、不压缩。图片存储机制将来要与 Evidence 共享,而 Evidence 的截图要交付进 Excel,画质一旦压掉无法找回。

列表页**不加载图片原图**,否则积累数百张截图后列表会变得很慢。

**Review 后的修正**

- **`.svg` 不再是可接受的截图扩展名。** SVG 是可执行脚本的文档,而图片由本服务同源提供 —— 正文里一个相对链接点开就是一个能调本机后端的页面,绕过 Markdown 渲染那道闸(design.md §6 F1 的攻击链)。非白名单扩展名一律记为 `.png`,字节不动;图片响应加 `X-Content-Type-Options: nosniff`。
- **「保存之前图片不落盘」这条以前不成立。** 一批图里有一张 base64 坏掉时,前面几张已经写盘,事务回滚,留下一个没有 memo 的目录。改为**先把所有图片解码完再写任何一张**,写盘途中出错则回收自己建的文件与目录。
- **新 memo 会继承残留目录里的图。** SQLite 会把回滚或删除掉的 memo 的 id 再发一次,而 `image_count` 是数目录里的文件数得来的 —— 于是一条从没放过图的新 memo 显示「含 1 张图」,展开是上一条 memo 的截图,删掉它还会把那个文件一并删掉。改为**创建时先清掉同 id 的残留目录**:一条正在创建的 memo 不可能已经有图。
- 上传加了 25MB 上限,`b64decode` 加 `validate=True`。
- 前端 `useImageAttachments`:插入位置以前是在 `await fileToDataUrl` **之前**抓的快照,读大截图那几十毫秒里敲的字会被覆盖。改为读完文件再看光标在哪。
- 前端保存成功后以前无条件清空整个待传列表,包括保存期间新粘进来、正文里还引用着的那张 —— 会在正文里永久留下一个 `![image](temp:…)` 死链。改为只忘掉**这次确实传上去了的那些**。
