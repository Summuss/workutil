# Spec: 多语言界面(M4 / F6)

Status: ready-for-agent

## Problem Statement

界面文案现在全是写死的中文,没有任何 key 层、没有语言包、没有切换机制。工作机在日本使用,界面显示日语会更贴合使用场景;同时也希望能在同一台机器上按需切换语言。这不是一次性加两个字符串,而是要先把「文案」从代码里独立出来,再决定怎么选、怎么记、缺了怎么办 —— 这套机制搭好之后,以后每加一处新文案都要过这道门。

## Solution

导航栏加一个语言开关(中文 / 日语)。首次打开按浏览器语言自动选一个,之后手动选过的会被记住(存在这台机器的浏览器里,不经过后端)。切换后,界面上所有你自己写的固定文案、以及操作失败时看到的错误提示,都变成所选语言;时间戳的显示格式也跟着换。你自己录入的 memo / todo / 书签 / evidence 内容永远不翻译。

机制是「key 查语言包」:每处文案在代码里是一个 key(如 `todo.empty_state`),实际显示的字由 `zh.json` / `ja.json` 决定。某个 key 在当前语言下没有翻译,就直接显示 key 本身,不悄悄 fallback —— 这是留给自己的「漏翻」信号,并且往后由一个自动化测试守住:`zh.json` 与 `ja.json` 的 key 集合必须完全一致,少一个就让测试失败。

## Implementation Decisions

完整推导在 `docs/design.md` §6 F6,这里只列结论与理由。

### 架构

- 自研极简 i18n:`t(key)` 函数 + React Context(当前语言 + 切换方法)+ 两个 JSON 语言包(`frontend/src/shared/i18n/zh.json`、`ja.json`)。**不用 react-i18next** —— 现在的规模(45 个源文件、两种语言、无复数 / 插值需求)不值得引入一个中等大小的依赖,真需要那天再换,替换面只在 `shared/i18n/` 内部
- `<html lang>`(`frontend/index.html`,现在硬编码 `"zh"`)跟随当前语言同步更新

### 默认语言与持久化

- 首次访问时读 `navigator.language`,匹配 `zh`/`ja` 前缀;两者都不是则兜底 `zh`(现状全部是中文)
- 手动切换后的选择存 `localStorage`,覆盖探测结果。**不经过后端、不做设置页面** —— 语言是目前唯一的用户偏好,单独起一个 Settings 模块是过度设计;持久化落在浏览器本地也和「两台机器数据各自独立」的既有架构一致
- 切换器是 `AppNav.tsx` 里的一个下拉,不是新页面

### 缺失 key 的兜底

- 渲染裸 key 本身(如 `[todo.empty_state]`),不静默 fallback 回中文。开发时一眼可见,比生产环境更「干净」但漏翻不可见更符合这个项目的使用方式(自己是唯一用户,也是唯一测试者)

### 后端错误信息

- **这次范围包含它**,不是只做界面文案:`backend/app/modules/{memo,todo,bookmark,evidence}/service.py` 里现有的自定义异常(`EmptyTitle`、`PathDoesNotExist` 等,目前是裸中文 / 偶尔英文字符串,详见 `backend/app/modules/*/service.py` 与 `frontend/src/shared/api.ts:20-28` 的 `refusalFrom`)统一改成带一个 `code` 字段;`router.py` 把 `code` 放进 HTTP 4xx 响应体;前端 `refusalFrom` 从「原样显示 `detail` 字符串」改成「用 `code` 查语言包」
- 未分类的非预期异常(500)保留一条通用的、已翻译的「未知错误」文案,不逐个分配 code —— 那些是 bug 该被修,不是需要打磨措辞的用户提示

### 时间格式

- `frontend/src/shared/time.ts:12` 现在硬编码 `toLocaleString("zh-CN", ...)`,改成读当前语言(`zh-CN` / `ja-JP`)。只换一个参数,不需要翻译 key

### 不受影响的部分

- Evidence 导出的 Excel:文件名已经是既定的日语命名约定(`エビデンス_<title>.xlsx`,`backend/app/modules/evidence/layout.py:141`),内容是自由格式的用户录入,两者都与这个开关无关,不在这次范围内改动
- 数据库里已有的 CJK 全文检索处理(`docs/adr/0002-substring-search-not-fts5.md`)是另一件事 —— 那是「怎么搜索用户内容」,这里是「界面显示什么语言」,互不影响

## User Stories

1. 作为在日本工作的开发者,我希望工作机上的界面能显示日语,更贴合使用场景。
2. 作为同一个人,我也希望能在同一台机器上随时切回中文,或者切到日语练习。
3. 作为只用一次的新访客场景(比如换了台新电脑),我希望第一次打开就显示一个合理的默认语言,不用先手动设置。
4. 作为长期用户,我希望切换一次之后,以后每次打开都记得这个选择,不用每次都切。
5. 作为开发者,我希望切到日语后,不只是按钮菜单变了,操作出错时看到的提示也是日语 —— 半中半日的报错框比全中文更让人分心。
6. 作为唯一的开发者兼用户,我希望某处翻译漏了的时候能立刻看出来,而不是被静默的中文兜底糊弄过去,导致这处漏翻永远没人发现。
7. 作为以后继续给这个项目加功能的开发者,我希望「新文案要中日都写」这件事有工具帮我守住,而不是全凭当时记不记得。

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| `zh.json` / `ja.json` key 对齐 | ✅ **主接缝** | 断言两份语言包的 key 集合完全相同。这是「新文案必须中日一起提交」这条工作流规则唯一的强制手段 |
| 后端错误 code(HTTP API) | ✅ | 触发一次已知校验失败(如空标题的 Todo),断言响应体带的是 code 而不是裸中文字符串 —— 守住「不再透传 Python 异常消息」 |
| `t()` 的 fallback 行为 | ❌ | 逻辑薄(查不到就返回 key 本身),读代码即可确认,不值得单独测 |
| 各页面文案覆盖是否完整 | ❌ 人工 | 属于「翻译内容对不对」而非「机制对不对」,过一遍界面比写断言可靠,也是「一次性全量翻译」这条验收本身要靠人眼确认的部分 |

### 必须存在的用例

- `zh.json` 缺一个 `ja.json` 有的 key(或反之)时,key 对齐测试失败
- 提交一个空标题的 Todo,响应体里能读到一个稳定的 code(不是中文提示原文)

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 第三种语言(如英语) | key + 语言包的架构已经为它留了口子,但这次只交付中日两种 |
| 独立的 Settings 页面 | 语言开关放在导航栏,不为它新建模块 |
| Evidence 导出 Excel 的语言 | 已有独立的日语命名约定,与界面语言开关无关,见「不受影响的部分」 |
| 相对时间文案(如「3 天前」) | 代码库里目前不存在这类文案(已核实),不需要处理 |
| 用户录入内容的翻译 | memo / todo / 书签 / evidence 里你自己写的内容永远原样显示 |
| 语言随账号 / 服务端同步 | 本工具没有账号概念,偏好只存在浏览器 `localStorage` 里,天然按机器区分 |

## Further Notes

### 为什么后端错误信息被拉进了这次范围

最初设想是「只做界面文案,后端校验错误(如 `service.py` 里的裸字符串)先不管」。但实际翻代码发现:前端 `shared/api.ts` 的 `refusalFrom` 是把后端 `detail` 字段原样显示给用户的,中间完全没有 key 层,而且 `memo/service.py` 的错误提示已经是英文、和其他模块的中文不一致。这意味着如果不管,日语模式下会不定期弹出中文(甚至英文)报错框 —— 这个不一致比想象中更显眼,所以改为这次一并处理。

### 为什么放在 M4,而不是更早

界面文案量在 M0–M3(骨架 + 四个功能模块)期间还在变。等架构和四个功能模块都稳定之后再抽取翻译,返工最少 —— 提前做的话,后面每加一个字段就要再补一次两种语言。
