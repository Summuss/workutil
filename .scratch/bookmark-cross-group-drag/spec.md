# Spec: 书签跨组拖拽

Status: ready-for-agent

## Problem Statement

一条散装书签要放进某个分组,今天只有一条路:点开它的编辑表单,在下拉框里选一个组,保存。攒一个「每天早上要开的那批」需要对每条书签走一遍这个流程 —— 而这个动作在直觉上就是「把它拖过去」。

拖拽本身已经有了(`drag-reorder` 那轮做的),但**只在同一个容器内**:`shared/sortable/index.tsx` 里每个 `SortableList` 各自带一个 `DndContext`,跨列表拖拽在结构上就不可能。

## Solution

把整个书签页收进**一个共享的 `DndContext`**,允许书签在「散装区 ↔ 任意分组 ↔ 另一个分组」之间任意方向拖动,落在鼠标松开的位置。分组之间原有的排序拖拽保持可用。

后端加一个**原子的「移到某个组的第 N 位」**操作,一次请求同时改归属和两侧的序号。

## Domain Model

不引入新概念,`CONTEXT.md` 不改。

一个 Bookmark 属于**零或一个** Group(ADR-0006)这条不变 —— 拖拽只是换了个方式修改 `group_id`,编辑表单里的下拉框本来就能做同一件事。

有一条要留意的张力:Group 的定义是「一批**要一起打开**的 Bookmark」,不是分类。拖拽把「加入组」变得非常轻,可能诱使把组当抽屉用。**定义不改** —— 降低操作成本没有改变组的含义;哪天真想要一个分类抽屉,那要先改 `CONTEXT.md`,而不是把这个功能悄悄做成分类。

## User Stories

1. 作为使用者,我希望把一条散装书签拖进某个分组,而不是打开它的编辑表单选下拉框。
2. 作为使用者,我希望把书签从一个组拖到另一个组,也能把它从组里拖回散装区 —— 拖错了不用回去开表单改。
3. 作为使用者,我希望书签落在我松手的那个位置,而不是一律被追加到组末尾 —— 组内顺序就是一键全开的打开顺序。
4. 作为使用者,我希望能把书签拖进一个**还是空的**分组(新建的组第一条就是这么来的)。
5. 作为使用者,我希望拖动过程中被拖的那条始终看得见,不会在滚动区边缘被裁掉一半。
6. 作为使用者,我希望分组之间原有的拖拽排序照常可用,不会因为现在能拖书签了就互相打架。
7. 作为使用者,我希望拖动失败(比如后端报错)时列表回到原样,而不是留在一个组里显示着、刷新后又跳回去的状态。

## Implementation Decisions

### 前端:一个 DndContext

- `BookmarkPage` 外层包一个 `DndContext`,内部的分组列表、每个组内的书签列表、散装列表都降级为 `SortableContext`。`shared/sortable/index.tsx` 要拆出「自带 context 的 `SortableList`」(其余四处继续用)和「只提供 context 的容器 + 纯 `SortableContext` 的子列表」两种用法。
- **必须引入 `DragOverlay`。** 现在的拖拽是「原地半透明 + transform 位移」,没有浮层;`fixed-layout` 之后内容区是 `overflow` 滚动容器,拖出容器边缘的元素**会被裁掉**,而跨组拖拽必然跨越容器边界。`DragOverlay` 渲染在 portal 里,不受祖先的 overflow 影响。
  - 这会**统一改变所有五处已有拖拽**的观感(todo、evidence 用例、block、书签、分组):被拖的东西变成跟随光标的浮层,原位留一个占位空槽。这是升级不是回归,但要在 `docs/running.md` 里让人对着看一遍。
- **空组要能接住。** 空组里没有任何 item 可以当落点,组容器本身注册成 droppable;拖拽进行中,空组显示一块虚线占位区(「拖到这里」)。
- **两种可拖动的东西要分开。** 同一个 context 里现在有组和书签两类,靠 dnd-kit 的 `data.type` 区分:拖书签时组不作为兄弟节点参与重排,拖组时书签同理。拖组仍然只能从组标题的把手发起。
- 乐观更新:松手立刻在本地把书签挪过去,请求失败则整体回滚到拖动前的快照并报错(现有 `handleReorderBookmark` 已经是这个形状,扩展它)。
- 编辑表单里的分组下拉框**保留**。键盘操作、以及「组太多、拖很远」的场景仍然需要它。

### 后端:一次原子请求

- 扩展书签的 move 端点,请求体带上目标组:`{to: 索引, group_id: 目标组 id 或 null}`。服务端在一个事务里改 `group_id`、给目标组的兄弟重排、也给**原来那组**的兄弟重排(它少了一条,序号要收拢),返回受影响的两个列表。
- **不要改 `core/ordering.py` 的 `MoveRequest`。** 那个类型被 todo、evidence、bookmark 三个模块共用(`app/modules/*/schemas.py` 各自 re-export),给它加 `group_id` 等于让 todo 和 evidence 也长出一个它们没有的概念。在 bookmark 模块里定义自己的请求 schema。
- **不走「两步」(先 PATCH `group_id` 再 move)。** 中间态是真实的:改完归属、排序请求失败,书签就落在新组的末尾而不是松手的位置;而且前端的乐观回滚要处理两个列表两次失败,比原子接口复杂得多。
- 目标组不存在 → 404;`group_id: null` 表示散装区,是合法目标。
- `to` 沿用现有的钳制语义(越界夹到 `[0, len-1]`),不算错误。

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| HTTP API:跨组移动 | ✅ 主接缝 | 归属改了、目标组序号连续、**原组序号收拢**、散装 ↔ 组两个方向、移进空组、目标组不存在时 404 |
| HTTP API:同组内移动 | ✅ 回归 | 带上 `group_id` 等于原组时行为与现在一致 |
| 前端拖拽交互 | ❌ | 沿用本仓库一贯做法,手动跑 `/run` 验证 |

「原组序号收拢」是最容易漏的一条:书签走了之后原组留下 `0,1,3` 这样的空洞,`Ordered` 契约要求连续。

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 一次拖多条 | 多选本身就是一套新交互,而这是低频整理动作 |
| 拖拽创建新分组(拖到「新建组」区域) | 先建组再拖两步够用 |
| 分组折叠 / 展开 | 与本次无关,组多到需要折叠时再说 |
| 跨 Case 拖 Block、跨列表拖 Todo | 那是各自领域的问题,不是这次顺手能带的 |
| 触屏优化 | 目标机器都是桌面端 |

## Further Notes

### 这是对 `drag-reorder` spec 的一次范围扩张

`.scratch/drag-reorder/spec.md` 的 Out of Scope 明确写着「跨组 / 跨 Case 拖拽:能力扩展,超出『把按钮换成拖拽』这个范围,以后单独提」。这份 spec 就是那个「以后」,只提书签一处;Evidence 的跨 Case 拖 Block 仍然不做。

### 依赖 `fixed-layout` 先落地

`DragOverlay` 那条的理由(滚动容器裁剪)来自 `fixed-layout`。反过来做的话,`DragOverlay` 会显得像一个没有理由的重构。
