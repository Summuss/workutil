# Spec: 复制用例

Status: ready-for-agent

## Problem Statement

一份 Evidence 里的几个用例常常长得**几乎一样**:同一套事前准备的 DB 数据、同样的画面顺序、同样的小标题,只有中间一两个值不同。现在只能新建一个空用例,再把每个 Block 重新贴一遍 —— 而截图和表格是贴不回来的,得回到原始来源重新取。

## Solution

在用例工具栏加一个**复制**按钮:复制出一个内容完全相同的新用例,插在原用例的紧后面,自动切过去,并**立刻进入重命名状态**(名字已预填好并选中,直接打字覆盖,或按回车接受)。

## Domain Model

不引入新概念。有一条既有的领域约束决定了这个功能的形状:

**Case 的 `name` 是测试用例编号,也就是导出后的 sheet 名**(CONTEXT.md / ADR-0003)。它同一份 Evidence 内不能重名(大小写折叠后比较)、最长 31 字符、不能含 Excel 的非法字符。所以「复制」不可能是一次无参数的动作 —— 新用例必须有一个新编号,而自动生成的编号几乎一定不是记录者想要的那个(真实编号长 `2~5` 这样)。这就是「自动命名 + 立刻进入重命名」而不是纯自动或纯弹窗的原因。

## User Stories

1. 作为使用者,我希望把一个已有用例连内容一起复制成新用例,不用把截图和表格重新取一遍。
2. 作为使用者,我希望复制之后马上就能改编号 —— 不用先接受一个 `1 (2)` 再去找重命名按钮。
3. 作为使用者,我希望新用例出现在原用例的紧后面,而不是被扔到最末尾。
4. 作为使用者,我希望复制完就在新用例里,可以直接开始改内容。
5. 作为使用者,我希望**删掉复制出来的用例,不会把原用例的截图一起弄没**。
6. 作为使用者,我希望原用例里 Block 的顺序、小标题、表格的表头设置在副本里原样保留。

## Implementation Decisions

### 图片必须连文件一起复制

这是本 spec 唯一有真正风险的地方。Evidence 的图片是**结构化引用、不做引用计数**(design.md §5):一个 image Block 就是一张图,`delete_case` 会把该用例名下所有 `image_name` 对应的文件从磁盘删掉。

所以副本的 image Block **绝不能共享原来的 `image_name`** —— 那样删掉副本会连带删掉原用例的截图(User Story 5),而且是静默的、不可逆的。复制时必须在同一个 evidence 的图片目录里把文件**另存为一个新名字**,沿用 `core/images.py` 现有的命名机制。

### 命名

- 建议名:`原名 (2)`,撞了继续 `(3)`、`(4)`…(大小写折叠后比较,和 `_refuse_duplicate_name` 同一套规则)。
- **31 字符上限要处理**:如果 `原名 + 后缀` 超长,**截断原名**以容纳后缀,而不是拒绝复制。这是硬约束(sheet 名),不能靠「大概不会有人取那么长」蒙混。
- 生成的建议名走一遍 `validate_case_name`,保证它自己不会造出一个非法名字。

### 接口

- `POST /api/evidence/{evidence_id}/cases/{case_id}/duplicate`,请求体为空(名字由服务端生成)。
- 返回**整个 cases 列表**,和现有 `move` 端点一致 —— 插入会改变后面所有用例的 `order`,只回新用例会让前端拿到过期的序号。
- 响应里要能认出新用例是哪个(列表 + 新 case 的 id,或前端按 id 差集算)。
- 原用例不存在 / 不属于这份 evidence → 404,沿用 `get_case` 已有的判定。

### 复制的内容

| 复制 | 不复制 |
| --- | --- |
| 所有 Block,连同 `order` | `id`(新的) |
| `kind`、`label`、`text` | 时间戳(新用例是新建的) |
| 表格的 `rows` 与 `has_header` | |
| 图片文件(另存为新名字)与新的 `image_name` | 原来的 `image_name` |

`rows` 是 JSON 列、按标识跟踪,复制时要**赋一个全新的列表**,不能把原对象挂到新行上(`models.py` 里那条注释说的就是这个坑)。

### 前端

- 复制按钮放在用例标签栏下方的工具栏里,「重命名」旁边;复制图标新增到 `shared/icons.tsx`,沿用 feather 描边风格。
- 请求返回后:切到新用例 → 立刻把它的标签切成 `InlineEdit`(初始值是服务端给的建议名,**全选**),回车接受、`Esc` 也接受(名字已经是合法的,取消编辑不等于取消复制)。
- 复用现有的 `caseEdit` busy 态置灰按钮。复制图多的用例会有明显延迟(逐个拷文件),**不加进度条、不设图片数量上限** —— 自用工具,一份 evidence 的量级撑不到需要它。
- 文案两种语言:`evidence.duplicate_case`、以及复制失败的提示。

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| HTTP API:复制的内容 | ✅ 主接缝 | Block 数量、顺序、label、文字、表格 rows 与表头全部一致 |
| HTTP API:图片文件 | ✅ **重点** | 副本的 `image_name` 与原件**不同**,两个文件都在磁盘上;**删掉副本之后原件的文件仍在** —— 这是 User Story 5,也是这个功能唯一会造成数据损失的失败模式 |
| HTTP API:命名 | ✅ 主接缝 | `1` → `1 (2)`;连续复制得到 `(3)`;长名字被截断且总长 ≤ 31;生成的名字不与任何现有用例重名 |
| HTTP API:位置 | ✅ 主接缝 | 新用例紧跟原用例,后面所有用例的 `order` 连续 |
| 前端交互 | ❌ | 沿用本仓库一贯做法,手动跑 `/run` 验证 |

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 跨 Evidence 复制用例 | 图片要跨目录搬,而且「把 A 的用例挪到 B」是另一个动作,不是这次的形状 |
| 复制整份 Evidence | 同上,以后要真需要再单独提 |
| 复制单个 Block | 用例内复制一段的需求还没出现过 |
| 由使用者指定新名字的弹窗 | 「立刻进入重命名」已经覆盖,再加一个弹窗是两套 |
| 复制进度条 / 图片数量上限 | 自用工具的量级用不上 |

## Further Notes

### 为什么不是「复制到剪贴板再粘贴」

看起来更通用,但 Evidence 的粘贴通道已经被占了:`add_pasted_block` 认的是浏览器剪贴板里的图片和表格。让它再认一种「workutil 自己的用例」格式,等于在一个已经要分辨三种内容的入口上再加一层判断,而收益只是省掉一个按钮。
