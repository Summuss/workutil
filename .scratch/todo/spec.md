# Spec: Todo(M3)

Status: ready-for-agent

## Problem Statement

待办事项是日常高频需求,现在没有承载的地方。而且有一个别的工具给不了的场景:**在 memo 里写着写着,发现这其实是件要做的事** —— 那一刻它应该能一键变成待办,并且以后还能追溯回当时写的上下文。

## Solution

一个列表:输入一行字回车,它就在那儿。做完点一下,它移进折叠起来的「已完成」区 —— 点错了能撤销,并且回到原来的位置。

顺序自己排(上下移动 + 置顶置底),因为优先级只有人知道。可以给一条加个截止日期,逾期标红、今天标橙,仅此而已 —— 它不参与排序,也不会弹通知。

在 memo 卡片上点「转 Todo」,弹出的输入框已经预填了 memo 的首行,改成一句像样的待办再确认。生成的 Todo 上有一条链接指回那条 memo —— 哪怕它已经旧到不在 memo 列表里。

## Domain Model

一层,术语见 `CONTEXT.md`:

```
Todo { id, title, order, due_date?, completed_at?, source_memo_id?, created_at }
```

`completed_at` 有值即已完成。`source_memo_id` **只是一个 id,不是外键**。

## User Stories

1. 作为开发者,我希望输入一行字就能记下一件待办,不需要填别的字段。
2. 作为开发者,我希望标记完成后它不再干扰我浏览没做完的事。
3. 作为开发者,我希望点错「完成」能撤销,并且它**回到原来的位置**。
4. 作为开发者,我希望还能看到已经做完的(默认折叠),因为「上周做完了什么」有价值。
5. 作为开发者,我希望自己排列先后,因为优先级只有我知道。
6. 作为开发者,我希望给某些待办加一个截止日期,并且**逾期和今天到期一眼可辨**。
7. 作为开发者,我希望没有截止日期的待办不会因此被排到末尾 —— 大多数待办本来就没有 deadline。
8. 作为开发者,我希望改掉一条待办的文字或删掉它。
9. 作为开发者,我希望在 memo 里发现「这是件待办」时,**在那条 memo 上**就能一键转出去。
10. 作为开发者,我希望转出时能当场改标题,因为 memo 的首行经常不是那件待办本身。
11. 作为开发者,我希望从 Todo 点回原 memo,**哪怕那条 memo 已经旧到不在列表里**。
12. 作为开发者,我希望原 memo 被删之后,那条 Todo 仍然好好的(只是没有链接可点)。

## Implementation Decisions

完整推导在 `docs/design.md` §6 F2,这里只列结论与理由。

### 列表与状态

- 排序**手工**(`order`),复用 evidence 的 `_reordered` / `Move`。
- **完成 / 撤销是两个独立动词**(`POST {id}/complete`、`POST {id}/reopen`),不是 `PATCH {done: true}` —— 状态转移是动词、字段编辑才是 PATCH,而且 `complete` 要顺带写 `completed_at`,藏进通用 PATCH 里迟早有人改了状态忘了时间戳。
- **完成时 `order` 不动**,撤销回原位。置底会让一次误点永久打乱手工排的优先级。
- **未完成全量返回、不设上限**;已完成区按 `completed_at` 倒序 + 上限(沿用 `RECENT_*_LIMIT` 的做法)。已完成区是唯一会无限增长、也是唯一不需要看全的地方。
- **不自动清理已完成项。**

### due_date

- 只到**日**,不带时分(带上就要处理时区和「几点算逾期」)。
- **不参与排序**,只显示:逾期红 / 今天橙 / 其余灰 / 无日期不显示。
- **不做提醒通知** —— 需要常驻进程,超出本工具形态。

### 从 memo 转出

- **`source_memo_id` 只存 id,不建 FK**;取不到就不显示链接。真 FK 要么让 memo 的删除路径关心 todo 表,要么依赖 SQLite 的 `PRAGMA foreign_keys` —— 都是让新功能反向污染旧功能,而「新增一个功能不应改动既有功能」是第一约束。
- **memo 那边不显示「已转成 Todo」**(那要求 memo 的查询去 join todo)。
- 回溯目标是新路由 **`/memo/:id`**(只显示那一条,渲染态可编辑,顶部「返回」)。**不能**做成「滚到列表里那一条」—— memo 列表有 `RECENT_MEMO_LIMIT`,老 memo 根本不在里面。
- 标题:转换时弹输入框,**预填正文首行**(`firstLine.ts` 已有),当场可改。不直接拿首行(它经常不是待办本身);不用选区(F1 那条「点正文进编辑会吃掉选区」的教训)。
- 入口在 **memo 卡片工具条**。这让 `features/memo` **单向**依赖 `features/todo` 的 api —— 知情的一处例外,反向永远不许;**后端 memo 零改动**。

### 接口面

| 动作 | 端点 |
| --- | --- |
| 新增(可带 `source_memo_id`)/ 改(title·due_date)/ 删 | `POST /api/todos` · `PATCH {id}` · `DELETE {id}` |
| 列表(未完成全量 + 已完成上限) | `GET /api/todos` |
| 完成 / 撤销 | `POST /api/todos/{id}/complete` · `POST /api/todos/{id}/reopen` |
| 排序 | `POST /api/todos/{id}/move` `{to: up\|down\|top\|bottom}` |

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| HTTP API | ✅ **主接缝** | 增删改、完成/撤销、排序、已完成区上限、指向已删 memo 的 todo |
| 前端 | ❌ | 没有值得测的逻辑 |

### 必须存在的用例

- **完成再撤销,todo 回到原来的位置**(守住「完成时 `order` 不动」)
- `source_memo_id` 指向一条**已删 memo** 的 todo **仍能正常列出**(守住「不建 FK」—— 有人会想加约束)
- 未完成项**不受上限影响**,已完成区**受上限**
- `due_date` 不同的两条待办,顺序仍然由 `order` 决定(守住「日期不参与排序」)

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 提醒 / 通知 | 需要常驻进程 |
| 重复待办 | |
| 子任务 / 分组 / 标签 | 和 memo 的标签同一个理由:归类本身是录入负担 |
| 已完成项自动清理 | 本地自用,攒不到需要清理的量 |
| memo 侧显示「已转成 Todo」 | 要让 memo 的查询 join todo,违反第一约束 |
| 按截止日期排序 / 筛选 | 大多数待办没有日期,排序键会失效 |
| 带时分的截止时刻 | 粒度从来不是小时 |

## Further Notes

### 这个功能会碰到 memo,而且是刻意的

M3 里唯一改动既有功能的地方:memo 卡片上多一个按钮、多一个 `/memo/:id` 路由。第一约束(「新增一个功能不应改动既有功能」)管的是**后端模块之间** —— 后端 memo 一行不动。前端这一处单向依赖是知情的,写在 design.md §6 F2 里。

`/memo/:id` 不碰 `/`:**打开工具仍然直接是输入框、光标已在里面**,F1 的零导航点击不能因为加了一个功能而丢掉(这是 M2 的 ticket 01 就立下的规矩)。
