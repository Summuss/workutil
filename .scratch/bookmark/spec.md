# Spec: 书签(M3)

Status: ready-for-agent

## Problem Statement

每次重启电脑,那几个每天都要开的文件得在文件管理器里一个个翻出来 —— 项目目录、那份配置、那个 Excel、那份文档。单次不过几十秒,但它是每次开机都要重来一遍的动作。

真正的痛点不是「打开一个文件」,而是「**一次要打开的是一批**」。所以这个功能的核心不是书签,是**组**。

## Solution

把常开的文件和文件夹一条条登记成 Bookmark,编进 Group,重启后点一下「一键全开」,这一组全部由系统默认程序打开。

登记靠粘贴路径(Windows `Shift+右键 → 复制为路径`,macOS `Cmd+Opt+C`),粘完当场校验:路径不存在直接拒绝,而不是收下一条以后打不开的死书签。列表里每条书签的有效性会在页面加载后单独检查一遍,失效的打灰标 —— 文件被搬走了,在点它之前就看得出来。

## Domain Model

两层,术语见 `CONTEXT.md`:

```
Group    { id, name, order }                        一批要一起打开的书签
  └─ Bookmark { id, group_id?, name, path, order }  一个指向本机文件或文件夹的入口
```

`group_id` 可空 —— 散装书签是合法的。**同一个 `path` 可以登记多条 Bookmark**,那不是重复:Bookmark 是一个入口,不是一个文件(ADR-0006)。

## User Stories

### 登记

1. 作为开发者,我希望粘贴一条路径就能登记一个书签,因为浏览器里没有别的办法拿到本机绝对路径。
2. 作为开发者,我希望粘错路径时**当场**被拒绝,这样列表里不会攒下永远打不开的项。
3. 作为开发者,我希望书签的名字默认就是文件名、但可以改,这样「config.yml」能被我叫成「A 项目的配置」。
4. 作为开发者,我希望文件搬了家时能改书签的路径,而不是删了重建。
5. 作为开发者,我希望**文件夹也能登记**,因为「打开项目目录」和「打开某个文件」是同一件事。
6. 作为开发者,我希望同一个文件能在两个组里各有一条书签、各叫各的名字。

### 编排

7. 作为开发者,我希望把书签编进组,因为我真正要的是「这一批」。
8. 作为开发者,我希望调整组内书签的先后,以及组自身的先后(「每日必开」应该在最上面)。
9. 作为开发者,我希望删掉一个组时,**里面的书签还在**,因为我只是想重新分组,不是不要这些文件了。
10. 作为开发者,我希望有些书签可以不属于任何组。

### 打开

11. 作为开发者,我希望点一下书签,文件由系统默认程序打开。
12. 作为开发者,我希望能打开文件所在的文件夹(文件夹书签除外 —— 没人想要父目录)。
13. 作为开发者,我希望**一键打开一整组**,这是这个功能存在的理由。
14. 作为开发者,我希望组里有一条失效时,**其余的照常打开**,并且明确告诉我跳过了哪几条。

### 失效

15. 作为开发者,我希望在点它之前就看得出某条书签已经失效。
16. 作为开发者,我希望失效检查不要拖慢列表 —— 一条指向已断开网络驱动器的路径能卡好几秒。

## Implementation Decisions

完整推导在 `docs/design.md` §3.3 / §6 F3,这里只列结论与理由。

### 平台层

- `core/platform.py` 只有 **`open(path)`** 和 **`reveal(path)`** 两个动词。文件和文件夹共用 `open` —— 两个平台上它们本来就是同一个调用。
- **F4 的执行脚本不进这一层**(那是 subprocess + 流 + 进程句柄)。
- **Linux 实现明确「不支持」,抛错,不调 `xdg-open`** —— 无 `DISPLAY` 时它有时退出码 0 却什么都没发生,当「支持」等于让开发时每一次验证都在撒谎。
- 平台层经 `deps.py` **注入**,HTTP 测试换成记录调用的 fake。这是本功能唯一的测试接缝设计,没有它整个功能在服务器上就只能靠肉眼。

### 登记

- **路径靠粘贴,不做文件选择器 —— 因为做不出来**:`<input type="file">` 的 `File` 没有 `path`,拖拽也没有。目录浏览器进 backlog(requirements.md §7)。
- **登记与改路径都校验存在性,不存在硬拒绝。** 不做「仍然登记」的二次确认。
- `name` 必填、由文件名预填;`path` 可改;不加备注字段。
- **不要给 `path` 加 `UNIQUE`,不要提示「已存在」**(ADR-0006)。

### 组

- 单亲:`bookmark.group_id` 可空。组内排序落在 `bookmark.order`,组自身有 `group.order`,两者都复用 shared/core 的 `_reordered` / `Move`(拖拽把手排序 + 保留置顶置底,详见 `.scratch/drag-reorder/`)。
- **删组 = 成员的 `group_id` 置空**,书签不删。

### 打开

- 一键开组:按 `order` **串行**、每个之间 **200ms**、**同步等完返回汇总**(`opened` / `skipped` 各是哪些、为什么)。失效跳过、其余照开,**不整组失败**(同 memo「删不掉文件不算失败」那条纪律)。不设条数上限。
- `reveal` 对文件夹书签回 **422** —— 前端不画这个按钮,后端也要有门。
- **能打开的就能执行**:指向 `.bat` / `.exe` 的书签点一下就是执行,知情接受,不加扩展名黑名单(ADR-0005)。

### 失效检测

- **单独的 `POST /api/bookmarks/check`**,不在列表接口里做 —— 在列表里做它就是阻塞的。
- 列表先渲染;**结果回来之前显示「未知」而不是「有效」**。

### 接口面

| 动作 | 端点 |
| --- | --- |
| 登记 / 改(name·path·group_id)/ 删 | `POST /api/bookmarks` · `PATCH {id}` · `DELETE {id}` |
| 组内排序 | `POST /api/bookmarks/{id}/move` `{to: top\|bottom\|<int>}` |
| 打开 / 打开所在文件夹 | `POST /api/bookmarks/{id}/open` · `POST /api/bookmarks/{id}/reveal` |
| 列表(按组 + 散装) | `GET /api/bookmarks` |
| 失效检查 | `POST /api/bookmarks/check` |
| 建组 / 改名 / 删组 / 组排序 | `POST /api/bookmark-groups` · `PATCH {id}` · `DELETE {id}` · `POST {id}/move` |
| 一键全开 | `POST /api/bookmark-groups/{id}/open` |

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| HTTP API | ✅ **主接缝** | 增删改、排序、删组、路径校验、失效检查 |
| 平台层(注入 fake) | ✅ **走主接缝** | 「点书签 → 平台层收到了这个路径」「开组 → 按序收到这几条」。**这是唯一能在开发服务器上守住打开逻辑的手段** |
| 真实的 `os.startfile` / `open` | ❌ 自动化 | 只能人眼验,留给 Windows 本机(design.md §9) |
| 前端 | ❌ | 逻辑都在后端,前端只是表单和列表 |

### 必须存在的用例

护栏,防止后来者(包括 AI agent)把已经想清楚的事「优化」掉:

- 一键开组时,fake 平台层**按 `order` 收到全部有效路径**,失效那条**没被传下去**且出现在 `skipped` 里(守住「跳过而非整组失败」)
- 开发平台(Linux)上调 open,接口回**明确错误**而不是 500(守住那条每天都会走到的错误路径)
- **删组之后成员还在**,`group_id` 变空(守住 ADR-0006)
- 登记一个**不存在的路径被拒**(守住「录入时校验」)
- **同一个 `path` 能登记两条**书签(守住 ADR-0006 —— 有人会想加去重)
- `reveal` 一个文件夹书签回 **422**

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 文件选择器 / 目录浏览器 | 浏览器不给绝对路径,唯一实现是后端列目录 —— 等于加一个「列出本机任意目录」的能力。登记是低频动作 |
| URL / 应用程序书签 | 浏览器自己的书签栏把这件事解决得更好 |
| 多对多分组(标签式) | ADR-0006 |
| 跨组拖拽 | 拖拽排序仅限同组内及分组间独立排序(详见 `.scratch/drag-reorder/`),跨组拖动书签超出范围 |
| 扩展名黑名单 | ADR-0005 |
| 打开后的结果确认 | `os.startfile` 是「交出去就不管」,系统有没有真的开出窗口,后端无从知道 |
| 图标 / 缩略图 | |

## Further Notes

### 这个里程碑最该早点做的一件事

平台抽象层是**全项目唯一在开发服务器上验不了**的东西(design.md §7 的落差)。M3 把它排在最前,就是为了让这个风险尽早暴露,而不是等 M4 的脚本执行时和进程管理搅在一起。注入 fake 之后,验不了的部分收缩成一句「系统真的开了那个窗口」。
