# Spec: Memo 置顶

Status: ready-for-agent

## Problem Statement

有几条 Memo 是**天天要看**的(常用命令、当前环境的连接串、一个反复要抄的编号)。它们和别的 memo 一样按时间倒序排,写下来第二天就沉下去了,每次要么翻要么搜 —— 而搜索是为「知道关键词但不知道在哪」设计的,这里的场景恰恰相反:知道在哪,只是它一直在往下沉。

## Solution

给 Memo 加一个**置顶**开关。置顶的 memo 在默认列表里排在最前面,按**置顶时间倒序**(最近钉的在最上),和下方的普通列表之间有一条视觉分隔。搜索状态下置顶不生效 —— 搜索是另一种视图。

数据上是一个 `pinned_at: datetime | None` 列:非空即置顶,值同时就是置顶区内的排序依据。

## Domain Model

**这会改 `CONTEXT.md`。** 现在的 Memo 词条和顶部那段对照说明写着 Memo「无序、长期沉淀、靠搜索捞回」,置顶引入了「一部分 memo 有位置」。

要写进词汇表的界限是:**置顶是「这条现在常用」这一个比特,不是分类**。它没有维度、没有名字、事后随手可开可关,因此不构成录入负担 —— 这正是 requirements.md §7 推迟「标签归类」的那条理由所针对的东西。同一段还要把「Memo 无序」修正为「除置顶外无序」,否则词汇表和代码互相打脸。

细节见 `docs/adr/0008-memo-can-be-pinned-but-not-categorised.md`。

## User Stories

1. 作为使用者,我希望把几条常用的 memo 钉在列表顶部,打开工具就能看到,不用翻也不用搜。
2. 作为使用者,我希望在折叠状态下就能钉/取消钉,不必先展开一条 memo。
3. 作为使用者,我希望**最近钉的排在最上面** —— 刚钉的那条就是我现在最关心的。
4. 作为使用者,我希望一眼看出哪些是钉住的、哪些是新写的,不会把一条钉了很久的旧 memo 误当成刚写的。
5. 作为使用者,我希望钉住一条很旧的 memo(比如三个月前写的)之后,它**永远**出现在顶部 —— 不会因为它已经掉出「最近 200 条」而消失。
6. 作为使用者,我希望一开始搜索,列表就是纯粹的搜索结果,置顶项不会赖在最上面挡着。
7. 作为使用者,我希望编辑一条置顶的 memo 之后,它还在原来的位置,置顶状态不受影响。

## Implementation Decisions

### 数据与查询

- `memos` 表加 `pinned_at: datetime | None`(可空,带 index),Alembic 迁移一条。**不加 `order` 列** —— memo 是全项目唯一没有显式顺序的实体,给它加 `Ordered` 等于放弃「memo 无序」这条领域定义;`pinned_at` 一个时间戳就够表达「最近钉的在最上」。
- **置顶必须是一次单独查询。** 列表接口硬性只取最近 200 条(`RECENT_MEMO_LIMIT`),一条钉住但很旧的 memo 会落在第 201 条之后 —— 如果只在同一次查询里排序,置顶对旧 memo 就是失效的,而那恰恰是最需要置顶的情况(User Story 5)。
- 默认列表 = `pinned_at DESC` 的置顶集合 + `created_at DESC, id DESC` 的最近 200 条,**后者要排除已在置顶集合里的**,否则一条最近写又被钉住的 memo 会出现两次。
- 置顶集合**不设条数上限**。自用工具,钉多了自己会取消;设上限要多一套「钉不下了」的文案和它的两种语言。
- 搜索路径完全不动:`_matching` 保持现状,置顶字段不参与排序、不参与过滤。
- `updated_at` 与 `pinned_at` 互不影响:改置顶状态**不算修改内容**,不动 `updated_at`(否则「修改于」会为一次点击而出现);编辑内容也不动 `pinned_at`。

### 接口

- `POST /api/memos/{id}/pin` 与 `DELETE /api/memos/{id}/pin`,返回更新后的 memo。用两个端点而不是一个 toggle:toggle 在双击或重放时结果不确定,而这两个是幂等的。
- 列表响应里每条 memo 带上 `pinned_at`(前端只用它判断是否高亮图钉,不用它排序 —— 顺序由服务端定)。

### 前端

- 图钉按钮在**折叠态和展开态都有**:折叠态放在右侧展开箭头的左边,展开态放进头部工具栏(转 Todo / 编辑 / 删除 那一排)。已置顶的图钉高亮,再点一次取消。
- 图钉图标新增到 `shared/icons.tsx`,沿用现有 feather 描边风格。
- 置顶区和普通列表之间一条分隔:一条细线加一个小标题(`置顶` / `ピン留め`)。没有这条线就分不清一条 memo 是新写的还是被钉住的(User Story 4)。
- 置顶区为空时**整个分隔和标题都不渲染**,不留一块空标题。
- 钉/取消钉之后列表就地重排,不整页刷新,不丢失已展开状态(`localStorage` 里那套按 id 记忆的展开状态不受影响)。
- 搜索状态下**不显示置顶区,也不显示图钉高亮以外的任何特殊处理** —— 图钉按钮本身还在(可以在搜到之后顺手钉住)。
- `SingleMemoPage`(`/memo/:id`)也放同一个图钉按钮,一致处理。
- 文案两种语言都要:`memo.pin` / `memo.unpin` / `memo.pinned_section`。

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| HTTP API:置顶 / 取消置顶 | ✅ 主接缝 | 幂等性、`updated_at` 不被动、置顶不存在的 memo 返回 404 |
| HTTP API:默认列表的顺序 | ✅ 主接缝 | 置顶在前、按 `pinned_at` 倒序、**不重复出现**、超出 200 条的旧置顶仍然返回 —— 最后一条是这个功能最容易悄悄坏掉的地方 |
| HTTP API:搜索路径 | ✅ 回归 | 搜索结果**不受**置顶影响 |
| 前端交互 | ❌ | 沿用本仓库一贯做法,手动跑 `/run` 验证 |

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 置顶区内手动拖拽排序 | 常用的通常只有 3～5 条,手动排序收益接近零,而它要给 memo 加 `order` 列 —— 那是放弃「memo 无序」的定义 |
| 置顶条数上限 | 自用工具,不值得为它加一套提示 |
| 搜索结果里的置顶 | 置顶和搜索是互斥的意图,见 User Story 6 |
| 标签 / 分类 / 收藏夹 | 仍然推迟(requirements.md §7),置顶不是它的第一步,见 ADR-0008 |
| 置顶 Todo / 书签 / Evidence | 它们本来就有显式顺序,可以直接拖到最前,不需要另一套机制 |

## Further Notes

### 为什么不复用已有的 `Ordered`

项目里 Todo、Bookmark、BookmarkGroup、EvidenceCase、EvidenceBlock 五处共享 `core/ordering.py` 的 `Ordered` + `reorder`,复用它是最省事的写法。**这里刻意不用**:那五处的顺序是「这批东西之间的先后关系」,是它们领域含义的一部分;memo 之间没有这种关系,`pinned_at` 表达的是「这一条现在常用」这个**单条属性**,不是条与条之间的秩序。用错模型的代价不是今天多写几行,而是往后每次看到 memo 有 `order` 列的人都会想「那这个顺序是谁定的、能不能拖」。
