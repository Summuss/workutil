# Spec: 数据导出与导入(换电脑)

Status: ready-for-agent

## Problem Statement

换一台工作电脑时,几个月攒下来的 memo、待办、书签、evidence 要跟着走。

requirements.md §7 曾经把这件事推迟掉,理由是「第一版只保证数据目录『整个拷走就是完整的』,手动备份已可行」。**真到要用的时候才发现,那句话只覆盖了一半:难的不是备份,是在新机器上放回去。**

- 那个目录在 Windows 上是 `%LOCALAPPDATA%\workutil`,得先知道它在哪、再手工翻进去
- 新机器上还要把东西放回同一个位置,而**那个位置在工具第一次启动之前根本不存在**
- 拷贝的那一刻工具可能正在写库 —— 库**没有开 WAL**(`create_engine` 不设任何 pragma,SQLite 默认是 rollback journal),撞上一个进行中的事务就会得到一个半新半旧或损坏的库。而发现的时候旧电脑可能已经不在手上了

## Solution

设置页上两个按钮:**导出数据**下载一个 zip;**导入数据**在新机器上把它装回去。

导入**只允许在工具还是空的时候执行**,不做合并。

## Domain Model

不引入新的领域概念 —— zip 是一个**机制**,不是概念,`CONTEXT.md` 不动。

后端模块叫 `transfer/`,是全项目**唯一没有 `models.py` 的模块**:它不拥有任何表,操作对象是整个数据目录。

## User Stories

1. 作为使用者,我希望在旧电脑上一键把全部数据导出成一个文件,不用去找数据目录在哪。
2. 作为使用者,我希望在新电脑上一键把它装回去,同样不用知道数据目录在哪。
3. 作为使用者,我希望导出的那一刻工具还能正常用,**导出的文件不是坏的**。
4. 作为使用者,我希望往一台已经有数据的工具里导入时**被明确拒绝**,而不是悄悄合并或覆盖。
5. 作为使用者,我希望用新版本导出的包去导入旧版本时**被明确拒绝**,而不是导进去之后打不开。
6. 作为使用者,我希望导入之后清楚地知道**要重启**。

## Implementation Decisions

### 导出

- **必须用 `sqlite3.Connection.backup` 取一份一致的快照**,不能直接拷 `workutil.db` 文件。理由见上 —— 这是这份 spec 里唯一一个「不做就会在最坏的时刻发现」的技术点。
- zip 内容:`workutil.db`(快照)+ `images/` 全部 + 一份 **manifest**(workutil 版本、alembic revision、导出时间、各表条数)。
- **走临时文件,不在内存里拼。** images 可能几百 MB,`BytesIO` 会直接把它顶进内存。写临时文件再 `FileResponse`,响应完删掉。
- 文件名 `workutil-data-<YYYYMMDD-HHMM>.zip`。ASCII,不需要 evidence 导出那套 RFC 5987 处理。

### 导入

四道门,顺序如下,**任何一道不过就整个拒绝,什么都不动**:

1. zip 结构合法(有 manifest、有 `workutil.db`)
2. manifest 的 **alembic revision 与当前应用一致** —— alembic 只会向前升级,把新版本导出的包塞进旧版本,结果是一个打不开的库
3. **所有业务表都没有行**
4. **`images/` 目录下没有文件**

**第 3 条的判据不能写成「db 文件不存在」** —— 启动时 alembic 已经把表建好了,那个文件一定存在。第 4 条不能省:「库空但图片还在」是上一次导入失败留下的现场,直接往上盖会留一堆孤儿文件。

过了四道门之后:

- **先把现有 `workutil.db` 改名成 `workutil.db.bak-<时间戳>`**,删除留给人手动。这是整个工具里唯一会覆盖既有数据的操作,哪怕判定它是空的。
- 解压 db 与 images 到数据目录。
- **提示手动重启,不自动重启。** SQLAlchemy 的 engine 还连着被换掉的那个文件。自动重启在便携包形态下要杀掉自己再拉起来,和既有的单实例逻辑(design.md §3.5)掺在一起只会更脆。

### 界面

- 新的 `/settings` 页 + 导航栏右侧一个齿轮图标。**不挂在语言切换旁边**:以后一定还会有别的设置,而「新增一个功能不应改动既有功能」是第一约束,一个页面比一个下拉菜单经得起加东西。
- **语言切换不搬进来。** 切语言是当场就要看到效果的动作,而且是唯一一个在任何页面上都可能想改的偏好;`/settings` 装的是「一次性的、要专门去做的」事。
- 四道拒绝各有各的文案,中日双份。

## Testing Decisions

| 位置 | 测? | 理由 |
| --- | --- | --- |
| HTTP API:导出 → 清空 → 导入往返 | ✅ **主接缝** | 造一份含 memo / todo / 书签 / evidence + 图片的数据,走完整条链路,逐项断言回来了 |
| **四道拒绝** | ✅ **重点** | 结构非法、revision 不匹配、库非空、images 非空 —— 每一条不拒绝就会毁数据 |
| 导出取的是一致快照 | ✅ 下沉 | 拿一个写到一半的库去测很难稳定,断言走的是 `backup` 调用路径即可 |
| 备份改名 | ✅ 主接缝 | 导入后数据目录里存在 `workutil.db.bak-*` |
| 前端两个按钮 | ❌ | 沿用一贯做法,手动跑 |

`WORKUTIL_DATA_DIR` 让整条链路都能在开发服务器上验完 —— **换一个数据目录就等于换一台新电脑**。

## Out of Scope

| 项目 | 说明 |
| --- | --- |
| 两台机器之间的数据**合并** | 要处理 id 冲突、图片重名、两边都改过同一条。而 requirements.md §3 说的就是两台机器各自独立,没有合并的场景 |
| 自动重启 | 便携包形态下要杀掉自己再拉起来,和单实例逻辑掺在一起更脆 |
| 增量 / 定时备份 | 换电脑是一次性动作,不是备份方案 |
| 选择性导出(只导 memo) | 没有这个场景;要的是「全都搬过去」 |
| 导出成人可读格式(Markdown / JSON) | 那是另一件事,形状完全不同,要逐个功能定格式 |
| 跨系统迁移时修复书签路径 | 书签存绝对路径是它本来的样子(ADR-0006),不是导入该管的事。running.md 里说明 |

## Further Notes

### 跨系统迁移,书签会全部失效

Windows → macOS 搬家之后,所有书签指向的 `C:\...` 在新机器上都不存在,会全部显示成失效项。**这不是 bug,是 Bookmark 本来的样子** —— 它是一个指向本机路径的入口(ADR-0006)。memo / 待办 / evidence 不受影响。写进 running.md,代码里不做任何补救:自动改写路径要猜「`D:\work\` 对应到 macOS 上的哪里」,猜错了就是把一批入口指向错误的地方。

### 为什么导入要这么保守

导入是整个 workutil 里**唯一会覆盖既有数据的操作**。其余所有破坏性动作(删 memo、删 Case、删 Evidence)都作用于单个对象、都有确认框、都是人当场指定的。这一个不一样:它一次覆盖全部,而触发它的人正处在「刚换了台电脑、什么都还没熟悉」的状态。四道门加一次备份改名,是和它的破坏半径相称的。
