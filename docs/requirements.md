# workutil 需求文档

> 本文只描述**要做什么**和**为什么**。技术选型与实现方式见 [design.md](./design.md)。

## 1. 背景与目标

日常开发中有一批**高频、琐碎、但一直没有好工具承载**的动作:

- 随手记的信息散落在记事本里,越积越乱、事后找不回来
- 常用文件散落在各个位置,每次重启电脑都要在文件管理器里一个个翻出来打开
- 想跑个小脚本,却要为此打开 IDE
- 改完功能要做验证 evidence,得手工往 Excel 里贴截图

这些事单个都不大,但每天重复,累积消耗可观。

**目标**:把它们收进一个统一的本地工具,降低每次操作的摩擦。

**这不是一次性项目** —— 以后想到新功能就会往里加。因此「新增一个功能的成本」是本项目的第一约束。

## 2. 使用环境

| 场景 | 环境 | 说明 |
| --- | --- | --- |
| 开发 | 家里的 Linux 服务器(Ubuntu 24.04) | 无桌面环境,从 macOS 远程连接 |
| 运行① | 工作用 Windows 电脑 | **主力使用场景** |
| 运行② | 私人 macOS 电脑 | |

工具需要在 **Windows 和 macOS 上都能使用**。

## 3. 前提与约束

| 项目 | 结论 | 理由 |
| --- | --- | --- |
| 两台机器的数据 | **各自独立,不同步** | 工作机的 memo / evidence / 书签留在工作机不外流,出于公司信息保密考虑 |
| Evidence 的 Excel 格式 | **自由格式**,由工具自己定 | 目前没有公司指定模板 |
| 工作机能否装软件 | **不需要装** | 实测工作机可在任意位置执行程序,而分发形态是解压即用的便携包,本来就不涉及安装 |

## 4. 功能需求

### F1. Memo(碎片信息记录)

**场景与痛点**
开发过程中经常产生一些琐碎信息需要记一下。目前记在记事本里,累积多了很难管理,想找的时候找不到。

**需求**

- 极低摩擦地录入 —— 打开就能写,写完即走
- 内容不只是文字,**有时包含图片**
- 事后能靠关键词快速找回
- 已记录的内容可以修改、可以删除
- 少数天天要看的 memo 可以**置顶**,打开就在眼前,不用翻也不用搜

**验收要点**

- 截图复制到剪贴板后,能直接粘贴进 memo 并正确保存、正确回显
- 打开工具时光标已经在输入框里,录入一条纯文字 memo 只需「输入 → 保存」
- 关键词能匹配到正文的**任意位置**,且结果要显示命中片段,而不是只显示开头
- 置顶一条**很旧的** memo(旧到已经不在列表里)之后,它依然稳定地出现在顶部
- 一眼分得清哪些是置顶的、哪些是刚写的
- 开始搜索后,列表就是纯粹的搜索结果,置顶项不会赖在最上面挡着
- **行为验收**:连续三天使用,期间没有再打开记事本

> Memo 没有标题字段 —— 强制起标题与「极低摩擦」直接冲突,而搜索已经实现了「以后好找」这个目的。
>
> **置顶不是归类**:它是「这条现在常用」一个比特,没有维度、没有名字、发生在记录之后,所以不构成录入负担。归类(标签)仍然不做,见 §7 与 [ADR-0008](./adr/0008-memo-can-be-pinned-but-not-categorised.md)。
>
> 数据导出**不在第一版范围内**,见 §7。

### F2. Todo List

**场景与痛点**
待办事项是日常高频需求。

**需求**

- 基础能力:新增、完成、删除、排序
- 可选:截止日期
- 与 F1 打通 —— memo 写着写着发现是个待办,能一键转成 Todo,并保留回溯到原 memo 的链接

**验收要点**

- 已完成项不干扰未完成项的浏览
- 误点「完成」之后能撤销,并且回到原来的位置
- 从 memo 转出的 Todo 能追溯回原 memo,**哪怕那条 memo 已经旧到不在列表里**

### F3. 文件书签

**场景与痛点**
常用文件散落在各个位置。**重启电脑后需要在文件管理器里一个个找出来打开,很不方便。**

**需求**

- 把文件**或文件夹**登记为书签,快速打开其中某一个
- **书签可分组,并且能一键打开一整组** —— 这才是真正解决「重启后逐个打开」的点,应作为核心能力而非附加
- 用系统默认程序打开文件
- 也能打开文件所在的文件夹
- 文件被移动或删除时,给出失效提示,而不是静默失败
- 登记时就能发现路径写错了,而不是等到某天点不开才知道
- 整理归属靠**拖动**:把书签拖进某个分组、拖到另一个分组、或拖回散装区,不用为此打开编辑表单

**验收要点**

- 在 Windows 上点击书签,文件由系统默认程序打开
- 一键打开分组后,该组内所有文件都被打开;**其中若有失效项,其余照常打开,并明确告知跳过了哪几条**
- 指向不存在文件的书签有明显的失效标识
- 登记一条路径写错的书签会被当场拒绝,而不是变成列表里一条永远打不开的项
- 把一条散装书签拖进分组,它落在松手的那个位置(组内顺序就是一键全开的打开顺序);拖错了能再拖出来

### F5. Evidence(验证証跡 → Excel)

**场景与痛点**
工作中修改完某个功能之后需要做验证,这个验证过程要整理成 evidence。目前全靠手工往 Excel 里贴截图、贴 DB 查询结果。

**evidence 文件长什么样**
一个 evidence 文件对应**一批测试用例**,每个用例占一个 sheet。sheet 名是测试用例编号,由记录者自己填,不一定是数字(`1`、`2`、`2~5`)。一个用例里通常有:事前准备的 DB 数据、画面截图、日志输出、DB 更新后的结果 —— 也就是**文字、图片、表格**三种内容,按顺序排下来,每段可以带一个小标题。

**需求**

- 方便地录入截图和文字
- **从 DB 客户端复制的查询结果能直接粘进来**,并保持行列结构,而不是变成一坨文字
- 一份 evidence 可以有多个测试用例;用例能增删、改名、调整先后
- 用例内的内容能调整顺序
- **一个用例能整个复制成新用例** —— 几个用例常常只差一两个值,截图和表格不该重取一遍
- 一键导出成**一个** Excel 文件,一个用例一个 sheet,图片嵌在里面

**验收要点**

- 连续粘贴多张截图并补充说明,过程中不需要切换到其他软件
- 从 IDEA 的 database 工具复制一段查询结果,粘进来是一张表格而不是一段文字
- 导出的 Excel 用 Excel / Numbers 打开时,sheet 名与用例编号一致,图片位置正确、不重叠、不溢出单元格
- DB 结果里的 `007`、日期、长 ID 在 Excel 里显示成原样,没有被自动转成数字、日期或科学计数法
- 复制一个用例后,新用例的内容与原用例逐段一致;**删掉复制出来的那个,原用例的截图仍然在**
- 复制之后可以马上改编号,不需要先接受一个自动生成的名字再去找重命名
- 完整走一遍「改完功能 → 粘贴截图 → 贴 DB 结果 → 补说明 → 导出 Excel」,耗时明显低于手工制作

> Evidence 的内容**没有步骤编号** —— 一个用例里的几段是分节(事前准备 / 画面 / 日志 / 结果),不是 1→2→3 的步骤,编号只会在插入一节时全部错位。每段改用一个可选的小标题。详见 [ADR-0003](./adr/0003-evidence-is-a-workbook.md)。

### F6. 多语言界面(中文 / 日语)

**场景与痛点**
现在界面文案全是写死的中文。工作机在日本使用,界面如果能显示日语会更贴合使用场景;同时也希望能在同一台机器上按需切换语言(比如练习日语,或单纯喜好)。

**需求**

- 界面提供中文、日语两种语言,可在导航栏手动切换
- 首次打开时按浏览器语言自动选定一种作为默认,之后手动选过的语言被记住,下次打开沿用
- 切换语言后,导航、按钮、菜单、空状态提示、确认弹窗等界面文案随之切换;操作失败时看到的错误提示(比如「待办内容不能为空」)也随之切换
- 时间戳的显示格式跟随所选语言

**验收要点**

- 切到日语后,遍历 memo / todo / 书签 / evidence 的每个页面,看不到遗留的中文界面文案
- 触发一次会报错的操作(如提交空标题的待办、登记一条不存在的路径),错误提示是日语
- 刷新页面或重新打开浏览器,依然是上次选择的语言
- 一台从未打开过 workutil 的日文系统浏览器,首次打开默认即为日语;中文系统浏览器首次打开默认为中文

> 你自己在 memo / todo / 书签 / evidence 里输入的内容永远不翻译,原样显示。Evidence 导出的 Excel 文件名与内容也不受这个开关影响,见 design.md §6 F5。

## 5. 非功能需求

| 项目 | 要求 |
| --- | --- |
| **可扩展性** | 新增一个功能不应改动既有功能。这是第一约束 |
| **跨平台** | Windows 与 macOS 均可使用 |
| **数据保密** | 工作机产生的数据不离开工作机 |
| **安全** | 工具具备执行任意本地代码的能力(F3 书签可指向 `.bat` / `.exe` / `.command`,见 [ADR-0005](./adr/0005-bookmarks-are-a-second-code-execution-path.md)),必须不可被外部访问 |
| **部署简单** | **不安装**:下载一个 zip、解压、双击即可用,不要求工作机上预先有 Python、Node 或任何别的东西 |
| **响应速度** | 本地工具,操作应即时;不接受为了打开一条 memo 而等待 |
| **界面稳定** | 每个画面的有效区域**固定不变**:展开一条 memo、切换一个用例、弹出一条提示,都不应让页面框架伸缩或让别的内容被推走。内容变多只体现为内部滚动条变长 |

## 7. 明确不做(Backlog)

刻意推迟的需求。列在这里是为了说明「这不是漏了」。

| 项目 | 为什么推迟 |
| --- | --- |
| Memo 标签归类 | 归类本身就是录入负担,与「极低摩擦」冲突。等搜索真的不够用了再加 —— 那时才知道该按什么维度分。**置顶不是它的第一步**:置顶没有维度也没有名字,不需要在记录的那一刻做任何决定,见 [ADR-0008](./adr/0008-memo-can-be-pinned-but-not-categorised.md) |
| 数据导出(打包 zip) | 第一版只保证数据目录「整个拷走就是完整的」,手动备份已可行 |
| 导入现有记事本内容 | 一次性动作,手动复制粘贴即可,不值得写代码 |
| 全局热键快速录入 | 受浏览器形态限制,需要额外的原生入口。先验证浏览器形态是否真的不够快 |
| 书签的文件选择器 / 目录浏览器 | 浏览器不把本地绝对路径交给页面,唯一的实现方式是由后端列出本机目录 —— 那等于给这个服务加一个「列出任意目录」的能力。而登记是低频动作,粘贴路径够用 |
| F4 Python 脚本管理与执行 | 目前用得不多,直接开 IDE / 终端跑也够用;而且是全项目里最独立、最复杂的一块(流式输出、进程管理、中断)。等真的高频需要再做,原有的设计草案(design.md 历史版本)留在 git 里备查 |

## 8. 已知风险

- **「极低摩擦」尚未被真实验证**:浏览器标签页无法注册全局快捷键,实际录入路径是「切到浏览器 → 找到标签页 → 输入」,未必快过一直开着的记事本。这是第一版最大的产品风险,由 §4 F1 的行为验收标准来检验。
