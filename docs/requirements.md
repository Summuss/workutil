# workutil 需求文档

> 本文只描述**要做什么**和**为什么**。技术选型与实现方式见 [design.md](./design.md)。

## 1. 背景与目标

日常开发中有一批**高频、琐碎、但一直没有好工具承载**的动作:

- 随手记的信息散落在记事本里,越积越乱、事后找不回来
- 常用文件散落在各个位置,每次重启电脑都要在文件管理器里一个个翻出来打开
- 想跑个小脚本,却要为此打开 IDE
- 改完功能要做验证 evidence,得手工往 Excel 里贴截图

这些事单个都不大,但每天重复,累积消耗可观。

**目标**:把它们收进一个统一的本地工具,降低每次操作的摩擦。

**这不是一次性项目** —— 以后想到新功能就会往里加。因此「新增一个功能的成本」是本项目的第一约束。

## 2. 使用环境

| 场景 | 环境 | 说明 |
| --- | --- | --- |
| 开发 | 家里的 Linux 服务器(Ubuntu 24.04) | 无桌面环境,从 macOS 远程连接 |
| 运行① | 工作用 Windows 电脑 | **主力使用场景** |
| 运行② | 私人 macOS 电脑 | |

工具需要在 **Windows 和 macOS 上都能使用**。

## 3. 前提与约束

| 项目 | 结论 | 理由 |
| --- | --- | --- |
| 两台机器的数据 | **各自独立,不同步** | 工作机的 memo / evidence / 书签留在工作机不外流,出于公司信息保密考虑 |
| Evidence 的 Excel 格式 | **自由格式**,由工具自己定 | 目前没有公司指定模板 |
| 工作机能否装软件 | **待确认** | 日本公司工作机常有限制,影响分发方式 |

## 4. 功能需求

### F1. Memo(碎片信息记录)

**场景与痛点**
开发过程中经常产生一些琐碎信息需要记一下。目前记在记事本里,累积多了很难管理,想找的时候找不到。

**需求**

- 极低摩擦地录入 —— 打开就能写,写完即走
- 内容不只是文字,**有时包含图片**
- 事后能靠关键词快速找回
- 已记录的内容可以修改、可以删除

**验收要点**

- 截图复制到剪贴板后,能直接粘贴进 memo 并正确保存、正确回显
- 打开工具时光标已经在输入框里,录入一条纯文字 memo 只需「输入 → 保存」
- 关键词能匹配到正文的**任意位置**,且结果要显示命中片段,而不是只显示开头
- **行为验收**:连续三天使用,期间没有再打开记事本

> Memo 没有标题字段 —— 强制起标题与「极低摩擦」直接冲突,而搜索已经实现了「以后好找」这个目的。
>
> 归类(标签)与数据导出**不在第一版范围内**,见 §7。

### F2. Todo List

**场景与痛点**
待办事项是日常高频需求。

**需求**

- 基础能力:新增、完成、删除、排序
- 可选:截止日期
- 与 F1 打通 —— memo 写着写着发现是个待办,能一键转成 Todo,并保留回溯到原 memo 的链接

**验收要点**

- 已完成项不干扰未完成项的浏览
- 从 memo 转出的 Todo 能追溯回原 memo

### F3. 文件书签

**场景与痛点**
常用文件散落在各个位置。**重启电脑后需要在文件管理器里一个个找出来打开,很不方便。**

**需求**

- 把文件登记为书签,快速打开其中某一个
- **书签可分组,并且能一键打开一整组** —— 这才是真正解决「重启后逐个打开」的点,应作为核心能力而非附加
- 用系统默认程序打开文件
- 也能打开文件所在的文件夹
- 文件被移动或删除时,给出失效提示,而不是静默失败

**验收要点**

- 在 Windows 上点击书签,文件由系统默认程序打开
- 一键打开分组后,该组内所有文件都被打开
- 指向不存在文件的书签有明显的失效标识

### F4. Python 脚本管理与执行

**场景与痛点**
经常要写一些小脚本。为了执行或编辑一个脚本单独打开 IDE 太重了。

**需求**

- 在工具内编写并保存 Python 脚本,带语法高亮
- 方便地执行
- 执行时输出**实时可见**,而不是跑完才一次性出现
- 支持传入参数、指定工作目录
- 执行时间过长时能中断
- 保留执行历史

**验收要点**

- 一个循环打印并 sleep 的脚本,输出是逐行滚动出现的
- 点击中断后,进程确实被终止(而非仅前端停止显示)

### F5. Evidence(验证証跡 → Excel)

**场景与痛点**
工作中修改完某个功能之后需要做验证,这个验证过程要整理成 evidence。目前全靠手工往 Excel 里贴截图、贴 DB 查询结果。

**evidence 文件长什么样**
一个 evidence 文件对应**一批测试用例**,每个用例占一个 sheet。sheet 名是测试用例编号,由记录者自己填,不一定是数字(`1`、`2`、`2~5`)。一个用例里通常有:事前准备的 DB 数据、画面截图、日志输出、DB 更新后的结果 —— 也就是**文字、图片、表格**三种内容,按顺序排下来,每段可以带一个小标题。

**需求**

- 方便地录入截图和文字
- **从 DB 客户端复制的查询结果能直接粘进来**,并保持行列结构,而不是变成一坨文字
- 一份 evidence 可以有多个测试用例;用例能增删、改名、调整先后
- 用例内的内容能调整顺序
- 一键导出成**一个** Excel 文件,一个用例一个 sheet,图片嵌在里面

**验收要点**

- 连续粘贴多张截图并补充说明,过程中不需要切换到其他软件
- 从 IDEA 的 database 工具复制一段查询结果,粘进来是一张表格而不是一段文字
- 导出的 Excel 用 Excel / Numbers 打开时,sheet 名与用例编号一致,图片位置正确、不重叠、不溢出单元格
- DB 结果里的 `007`、日期、长 ID 在 Excel 里显示成原样,没有被自动转成数字、日期或科学计数法
- 完整走一遍「改完功能 → 粘贴截图 → 贴 DB 结果 → 补说明 → 导出 Excel」,耗时明显低于手工制作

> Evidence 的内容**没有步骤编号** —— 一个用例里的几段是分节(事前准备 / 画面 / 日志 / 结果),不是 1→2→3 的步骤,编号只会在插入一节时全部错位。每段改用一个可选的小标题。详见 [ADR-0003](./adr/0003-evidence-is-a-workbook.md)。

## 5. 非功能需求

| 项目 | 要求 |
| --- | --- |
| **可扩展性** | 新增一个功能不应改动既有功能。这是第一约束 |
| **跨平台** | Windows 与 macOS 均可使用 |
| **数据保密** | 工作机产生的数据不离开工作机 |
| **安全** | 工具具备执行任意本地代码的能力(F4),必须不可被外部访问 |
| **部署简单** | 工作机上的安装步骤越少越好(受安装限制待确认影响) |
| **响应速度** | 本地工具,操作应即时;不接受为了打开一条 memo 而等待 |

## 6. 待确认事项

- [ ] 工作用 Windows 电脑是否允许自由安装软件 —— 影响最终分发方式,但不影响开始开发

## 7. 明确不做(Backlog)

刻意推迟的需求。列在这里是为了说明「这不是漏了」。

| 项目 | 为什么推迟 |
| --- | --- |
| Memo 标签归类 | 归类本身就是录入负担,与「极低摩擦」冲突。等搜索真的不够用了再加 —— 那时才知道该按什么维度分 |
| 数据导出(打包 zip) | 第一版只保证数据目录「整个拷走就是完整的」,手动备份已可行 |
| 导入现有记事本内容 | 一次性动作,手动复制粘贴即可,不值得写代码 |
| 全局热键快速录入 | 受浏览器形态限制,需要额外的原生入口。先验证浏览器形态是否真的不够快 |

## 8. 已知风险

- **「极低摩擦」尚未被真实验证**:浏览器标签页无法注册全局快捷键,实际录入路径是「切到浏览器 → 找到标签页 → 输入」,未必快过一直开着的记事本。这是第一版最大的产品风险,由 §4 F1 的行为验收标准来检验。
