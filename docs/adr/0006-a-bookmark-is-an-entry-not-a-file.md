# Bookmark 是一个入口,不是一个文件

「书签可分组」的第一直觉是把 Group 做成标签:多对多,一个文件挂在「每日必开」和「项目A」两个组里。我们**不这么做**:一个 Bookmark 属于**零或一个** Group,同一个路径要出现在两个组里,就登记**两条 Bookmark**。

这不是为了省一张关联表,而是因为 Bookmark 的身份是**一个入口**,不是它指向的那个文件。同一个 `config.yml`,在「每日必开」里叫「配置(每天要看的)」、排在第二位,在「项目A」里叫「A 的配置」、排在最后一位 —— 名字和位置本来就该各不相同。多对多模型没地方放这两套名字和两个位置,除非把它们再挂到关联表上,那时关联表就是 Bookmark 本身,只是名字取错了。

单亲还带来一个直接好处:组内排序落在 `bookmark.order` 上,可以原样复用 evidence 的 `_reordered` / `Move`(上下移动 + 置顶置底),连交互约定都不用重新定。

## Consequences

- **「这个路径已经登记过了」不是一个错误,不要去重。** 不要给 `path` 加 `UNIQUE`,不要在登记时提示「已存在」。那会把这个模型悄悄改回「Bookmark 就是文件」,而且是不可见地改回去。
- 代价是文件搬家时要改两处路径。这是低频动作,接受。
- 删掉一个 Group,成员**变成散装书签、不跟着删**。登记一个入口和编排一次开机要开哪批是两件事,删编排不该带走登记;而误删的补救是回文件管理器里重新翻出那些路径 —— 正是这个功能存在的理由所要消灭的动作。
- 允许「不属于任何组」的散装 Bookmark。强制建组会把摩擦压回录入侧,而书签的录入摩擦已经因为浏览器不给绝对路径而偏高了(design.md §6 F3)。
